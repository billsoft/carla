# 分步修复计划：从黑屏到高质量体素数据集 (UE5.5 光照与全流程修复)

针对 UE5.5 全新光线系统（Lumen）导致的黑屏问题，以及体素数据集生成的各个环节，制定以下详细修复计划。

## 第一步：修复 RGB 相机黑屏与画质 (UE5.5 Lumen 适配)

**目标**：恢复 8 个 RGB 相机的正常曝光、色彩和光照，使其与官方示例 (`manual_control.py`) 及旧版代码效果一致。

### 1. 问题根源分析 (UE5.5 光照系统)
*   **现象**：`dataset_output/cameras` 全黑。
*   **原因**：UE5.5 默认启用 Lumen 全局光照系统，该系统深度依赖**后处理管线 (Post-Process Pipeline)** 来计算间接光照和曝光。
    *   **GitHub/官方代码 (Good)**: 在 `manual_control.py` 中，明确设置了 `gamma=2.2`，并且针对 `Town10HD_Opt` 等高清地图，显式设置了 `post_process_profile='Town10HD_Opt'`。这告诉引擎加载特定的曝光和色调映射表（LUT），否则引擎不知道如何渲染天空光。
    *   **当前代码 (`core/rgb_suite.py`) (Bad)**: 仅开启了 `enable_postprocess_effects=True`，但**缺失**了 `post_process_profile`（导致光照配置未加载）和 `iso/shutter_speed`（导致默认曝光过暗）。

### 2. 修复行动
修改 `core/rgb_suite.py`，在 `_setup_sensors` 中补全缺失的光照配置：

```python
# 1. Gamma 校正 (标准 sRGB)
if bp_rgb.has_attribute('gamma'):
    bp_rgb.set_attribute('gamma', '2.2')

# 2. 地图专属后处理 (UE5 关键修复)
# 如果没有这个，Town10HD_Opt 会黑屏或曝光极差
map_name = self.world.get_map().name
if 'Town10HD_Opt' in map_name and bp_rgb.has_attribute('post_process_profile'):
    bp_rgb.set_attribute('post_process_profile', 'Town10HD_Opt')

# 3. 曝光控制 (防止画面过暗)
if bp_rgb.has_attribute('shutter_speed'):
    bp_rgb.set_attribute('shutter_speed', '200.0')
if bp_rgb.has_attribute('iso'):
    bp_rgb.set_attribute('iso', '1200.0')
```

**验证**：创建 `scripts/test_rgb.py` 采集 1 帧，确认图像明亮清晰。

## 第二步：修复深度图采集与保存

**目标**：确保 `dataset_output/depth` 包含正确的深度图数据。

### 1. 问题分析
*   **现象**：`depth` 目录为空。
*   **原因**：`main_data_collection.py` 获取了深度数据，但 `utils/data_saver.py` 中**根本没有** `save_depth` 方法。

### 2. 修复行动
*   **修改 `utils/data_saver.py`**：添加 `save_depth` 方法。
    *   **格式建议**：保存为 **16-bit PNG**。
    *   **逻辑**：将深度值（米）乘以 1000 转为毫米（uint16），保存为灰度图。这样既可视化方便（虽然看起来很黑，但在 Viewer 中拉伸后可见），又保留了精度。
*   **修改 `main_data_collection.py`**：在主循环中调用 `saver.save_depth(frame, depth_data)`。

## 第三步：God Mode 体素生成与颜色映射校正

**目标**：生成 ID 正确、颜色符合 17 类标准的体素数据。

### 1. 问题分析
*   **现象**：体素颜色混乱。
*   **原因**：`occupancy_viewer` 的颜色表 (`PALETTE`) 很可能是旧的（基于 CityScapes 或其他），与现在的 `config/occupancy_config.py` 中的 17 类标签（0-17）不对应。

### 2. 修复行动
*   **标签对齐**：检查 `config/occupancy_config.py`，确保 `CARLA_TO_OCCUPANCY_MAPPING` 严格映射到 `体素分类建议.md` 中的 0-17 类。
*   **Viewer 修复**：更新 `occupancy_viewer/run_viewer.py`，使其 `PALETTE` 数组严格对应 17 类（例如 ID 4=绿色/Car，ID 10=蓝色/Truck）。
*   **God Mode 验证**：在 `main_data_collection.py` 中临时注释 `vis_filter.run`，直接保存原始体素，验证几何结构和语义分类。

## 第四步：最终过滤与数据集生成 (Critical Logic)

**目标**：开启深度可见性过滤，生成最终 Dataset。

### 1. 逻辑对比 (Github Old vs New)
*   **GitHub/Old (`lidar_voxel_generator.py`)**:
    *   **过滤源**：基于 LiDAR 点云射线。
    *   **逻辑**：体素中心距离最近 LiDAR 点 < 阈值。
    *   **缺陷**：稀疏，细小物体（栏杆、自行车）因光线未击中而完全丢失。
*   **Current New (`core/visibility_filter.py`)**:
    *   **过滤源**：基于 360° 深度相机（稠密像素）。
    *   **逻辑 1 (Geometry)**：体素投影到深度图，检查 `dist < depth + 0.5m`。
    *   **逻辑 2 (Instance Completion - 关键改进)**：只要物体（Actor ID）有**任意部分**可见，**整体**保留。解决“空心车”问题。
    *   **逻辑 3 (Ground Protection - 关键改进)**：强制保留语义为地面的体素。解决远处地面丢失问题。

### 2. 修复行动
*   恢复 `main_data_collection.py` 中的 `vis_filter.run()`。
*   运行采集 5 帧。
*   检查最终产物：RGB（亮）、Depth（有）、Occupancy（实心且语义正确）。
